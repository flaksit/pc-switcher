## QUESTION 1 — VERSION DIVERGENCE (same item on both sides, different version/revision/channel)

### apt — reports only, never converges; installs by name, version floats
The base diff handles "present on both, differing versions" in `sync_core.py:293-303`: when `source_item.version != target_item.version` it emits `DiffClass.VERSION_MISMATCH` with `action=DiffAction.REPORT_ONLY`. The `apply()` loop explicitly excludes `REPORT_ONLY` from convergence (`sync_core.py:438-441`, `diff.action != DiffAction.REPORT_ONLY`), so a version difference produces a review item but is **never acted on** — no upgrade, no downgrade. The docstring at `sync_core.py:228-229` states this: "present on both with differing versions -&gt; `VERSION_MISMATCH`/`REPORT_ONLY` (D-04: reported, never force-downgraded)". Detail text is "source has X, target has Y" (`items.py:203-210`).

When apt *does* install (a missing package), it installs by **name only** — no version pin. `apt_sync.py:1063` builds `install -y --no-install-recommends {quoted}` (just the name); the real command at `apt_sync.py:1086` is `apt-get install ... {name}`. Version therefore floats to whatever the target's own repos offer.
- Net: version difference on an already-installed package → `REPORT_ONLY` review item, ignored for convergence.

### snap — forces source's exact revision AND channel; produces a CHANGE review item
Verified in code. `_diff_snap_items` (`snap_sync.py:183-188`) treats "present on both" where `source_item.revision != target_item.revision OR source_item.channel != target_item.channel` as a diff, building `_change_diff` (`snap_sync.py:143-160`): `diff_class=VERSION_MISMATCH`, `action=DiffAction.CHANGE`. Unlike apt, this is not `REPORT_ONLY`, so it converges. The docstring at `snap_sync.py:144-147` says "unlike apt package versions (D-04), both actively converge — never `REPORT_ONLY`".

Convergence forces the exact revision: `_converge_change` (`snap_sync.py:331-354`) runs `sudo snap refresh --revision={revision} {name}` when the revision differs (`snap_sync.py:344-346`), and `_switch_channel` runs `sudo snap switch --channel={channel} {name}` when the channel differs (`snap_sync.py:356-359`). The revision string comes from the captured source `SnapItem` (`snap_sync.py:298-309`, `_source_items_by_id`). So yes — snap lands the target on the source's exact revision and tracking channel. It is a CHANGE-group review item (default-checked, since CHANGE is not a removal direction — `review.py:88`, `_REMOVAL_ACTIONS = {"remove","delete","disable"}`).

### flatpak — does NOT converge version; REPORT_ONLY only, like apt
`_diff_flatpak_refs` (`flatpak_sync.py:247-248`): "present on both" same `item_id` (same application AND same scope) with `source_item.version != target_item.version` → `_version_mismatch_ref_diff` (`flatpak_sync.py:208-221`) with `action=DiffAction.REPORT_ONLY`. The docstring (`flatpak_sync.py:50-53`, `208-213`) is explicit: "a flatpak ref's version floats like an apt package's does — reported, never force-installed/removed to converge it." `converge()` for a ref only handles `REMOVE` and `INSTALL` and raises for anything else (`flatpak_sync.py:481-510`), and INSTALL just runs `flatpak install -y {scope_flag} {origin} {application}` (`flatpak_sync.py:504`) — no commit/version pin. So flatpak just ensures the ref is installed; a version difference is a report-only review item and is never converged to an exact commit.

### manual_installs — no version comparison at all
There is no target manifest and no version field compared. `query_target_items` unconditionally returns `[]` (`manual_installs_sync.py:318-325`, docstring: "No target-side manifest exists for unreproducible items"). `plan()` (`manual_installs_sync.py:327-363`) iterates only over source-detected items and decides the action solely by **snippet presence in the source registry**: `action = DiffAction.INSTALL if snippet is not None else DiffAction.REPORT_ONLY` (`manual_installs_sync.py:350`). "Differs" is never computed against the target — an item is `INSTALL` if it has a source-side snippet, else `REPORT_ONLY` (needs resolution). No version/revision comparison for `.deb`, `/usr/local`, or `/opt` items exists anywhere in the job.

Consequence for a target-only or differing entry: after the push the target file is byte-identical to the source file. An entry that existed on the target but not in the source is LOST (overwritten). Caveat on "lost": the source registry accumulates entries across runs via `add()` merges (state.py:361-382, last-write-wins by item_id), so the source file is usually a superset over time — but that is source-side history, not a target-side merge. Anything only ever authored on the machine currently acting as target is not preserved by this push.

## QUESTION 1 — SNAP CONFIG (hold/refresh control)

What snap_sync syncs per snap: **name, channel (tracking), and revision** — nothing else. `_parse_snap_list` builds each `SnapItem` from exactly three columns: `Name`, `Rev`, `Tracking` (`snap_sync.py:117`). Revision is forced via `snap install --revision=N` / `snap refresh --revision=N` (`snap_sync.py:324-326`, `344-346`).

Hold / refresh-inhibit state is **NOT synced**. The doc's claim holds:
- The module docstring explicitly states this job never calls `snap refresh --hold` and uses only `install --revision`/`refresh --revision`, which "land the target on the source's exact revision without touching the standing auto-refresh policy at all" (`snap_sync.py:6-13`).

Verdict: If a snap is held on the source, that hold does **NOT** travel to the target. The code never reads per-snap hold state on the source, so it has nothing to replicate; it never writes hold state on the target. Convergence is revision+channel only. `converge()` dispatches only to install / change / remove (`snap_sync.py:295-311`); no hold verb exists.

## QUESTION 2 — FLATPAK CONFIG (remotes + pin/mask)

Remotes ARE synced. They are a first-class item class (`FLATPAK_REMOTE`) captured, diffed, and converged:
- Capture: `_capture_all_source_remotes` / `_query_all_target_remotes` run `flatpak remotes --columns=name,url` once per scope (user + system) on each machine (`flatpak_sync.py:83-99` template `_FLATPAK_REMOTES_CMD_TEMPLATE` at line 88; loops at `386-399`).

# Design report: replicating apt hold state as synced Items (issue #208, apt scope)

## 1. CURRENT behavior — holds are read-only reports, never written

Confirmed exactly. `AptSyncJob.collect_hold_pin_facts` (`src/pcswitcher/jobs/apt_sync.py:586-621`) runs `apt-mark showhold` on **both** source and target and emits one `HoldPinFact(mechanism="hold", ...)` per line from each (lines 597-607). Those facts flow through `PackageSyncJob.plan()` (`sync_core.py:365`) into `diff_items` → `_diff_apt_packages`.

The guard that turns a hold into a report is `sync_core.py:248-258`:

```python
if target_item is not None and target_item.name in held_or_pinned:
    diffs.append(ItemDiff(item_class=APT_PACKAGE, diff_class=HELD_OR_PINNED,
                          action=REPORT_ONLY, ...))
```

Precedence: this branch is checked **first** for each item_id, so a held package never becomes INSTALL/REMOVE/VERSION_MISMATCH. Two important facts about the current guard:
- It keys on `target_item.name in held_or_pinned` and requires `target_item is not None` — so **a package held only on the source, absent on the target, produces no diff at all** (source-only holds are silently dropped; the source `showhold` read at line 597-601 is effectively dead for anything not also installed+present on the target).
- `REPORT_ONLY` diffs are excluded from converge in `apply()` (`sync_core.py:441`) regardless of decision, and skipped by `_record_permanent_skips` (`sync_core.py:523`).

Does hold state ever get written to the target? **No.** `grep` over `src/` finds only `showhold` (read). There is no `apt-mark hold`/`unhold`/`set-selections` anywhere. Expected result confirmed.

## 2. CLI facts — `apt-mark showhold` / hold semantics

Verified from `man apt-mark` (apt 2.8.3) on this machine:
- **`showhold`** — "print a list of packages on hold in the same way as for the other show commands." Output is **one package name per line**, no version, no priority. `showhold` exits 0 with empty output when nothing is held (verified live: `apt-mark showhold` → empty, exit 0).
- **`hold`** — "changes dpkg selections such as hold" — i.e. it is **dpkg selection state stored under `/var/lib/dpkg`**, not an apt-config file. It blocks automatic install/upgrade/**removal** of the package.
- **Arch/scope nuance:** the "same way as other show commands" means, on multiarch systems, foreign-arch packages are printed as `name:arch` (native arch printed bare). This is consistent with `apt-mark showmanual`, which the package manifest already parses the same way (`_resolve_versions`, `apt_sync.py:559-583`) — so `HoldPinFact.package` and `AptPackageItem.name` use the same `name[:arch]` spelling and will match. (Verified the spelling *convention* against the man wording; no foreign-arch hold existed live to observe directly.)
- **Hold on an uninstalled package:** hold is a dpkg *selection*, and dpkg selections can exist for not-currently-installed packages (this is how one pre-holds). Whether `apt-mark hold &lt;pkg&gt;` succeeds when the target has **no dpkg record and no apt-cache entry** for that name is the one fact I could **not verify without mutating state** (I did not run any hold). Documented behavior: it works for any package apt/dpkg knows (installed, or known-but-removed, or available in the cache); a wholly-unknown name is likely to error. **Flagged as a design question in §7.**

## 3. CONVERGE commands

- Add a hold: `sudo apt-mark hold &lt;pkg&gt;`
- Remove a hold: `sudo apt-mark unhold &lt;pkg&gt;`

**Sudo: yes** — hold/unhold write dpkg selection state under `/var/lib/dpkg`. (Contrast `showhold`, which needs no sudo; the existing `collect_hold_pin_facts` reads run without sudo, `apt_sync.py:597/603`.) The target already validates passwordless sudo (`validate()`, `apt_sync.py:1525`); `/usr/bin/apt-mark` would need adding to `_TARGET_SUDO_COMMANDS` (`apt_sync.py:75-82`).

**Idempotent: yes.** `apt-mark hold` on an already-held package is a no-op ("already hold"); `apt-mark unhold` on a not-held package is a no-op. Both exit 0. Safe to re-run.

## 4. DESIGN — hold as a first-class synced Item

Proposed item model, fitting the existing item→diff→review→converge pipeline:

**New item dataclass** in `packages/items.py` (a new `ItemClass.APT_HOLD = "apt_hold"`):
```
AptHoldItem(name: str)
  item_id -&gt; f"apt:hold:{name}"
  label() -&gt; f"{name} (hold)"
```
`item_id` scheme `apt:hold:&lt;pkg&gt;` is distinct from `apt:package:&lt;pkg&gt;` — critical so a package's install/version item and its hold item are two separate identities in the same review (de-dupe handled in §5).

**Capture (source) / query (target):** the *presence* of a name in `apt-mark showhold` is the item's existence. Model it exactly like a set-membership item: source-held names → source items, target-held names → target items. This slots into the existing diff engine, where existence-on-one-side-only is the whole signal.

**Diff directions** (both mean "make target match source"):
- source-held &amp; target-not-held → **add hold on target**
- target-held &amp; source-not-held → **remove hold on target**
- held on both, or held on neither → no diff.

**DiffAction:** Do **not** reuse INSTALL/REMOVE (those read as "install/remove the package" in `_ACTION_VOCABULARY`, `sync_core.py:113-120`, and would land in the package install/removal review groups — exactly the destructive-bulk-tick confusion D-07 guards against). Two clean options:
- **(a)** Use `DiffAction.CHANGE` for **both** directions (converging a flag to match source is a "change", and CHANGE is already treated as install-direction/checked-by-default, not a removal — `review.py:92` comment). Direction is then derived at converge time from which side holds it. Add vocabulary entries `(APT_HOLD, CHANGE): "hold"` and present add-vs-remove via the `detail` string.
- **(b)** Use INSTALL for add-hold and REMOVE for remove-hold, so remove-hold correctly lands in the separated removal group (unchecked by default — a good fit, since *removing* a user's deliberate hold is the direction that deserves the extra friction).

**(b) is the better fit for the existing grouping/default-checked machinery**: `_build_review_groups` (`sync_core.py:308`) already separates removals, and `_record_permanent_skips` (`sync_core.py:499-536`) already routes INSTALL/CHANGE→source-held-file and REMOVE→target-held-file for skip-always — which is exactly right for holds (an add-hold is source-held → skip-always recorded on source; a remove-hold is target-held → recorded on target). Add `(APT_HOLD, INSTALL): "hold"` and `(APT_HOLD, REMOVE): "unhold"` to `_ACTION_VOCABULARY`.

**Converge:** extend `AptSyncJob.converge` (`apt_sync.py:1062`) to dispatch `ItemClass.APT_HOLD`:
- INSTALL/add → `sudo apt-mark hold &lt;name&gt;`
- REMOVE/remove → `sudo apt-mark unhold &lt;name&gt;`

using `shlex.quote(name)` and `self.target.run_command(..., login_shell=False)`, returning the `CommandResult` (exit code decides pass/fail, D-27). No apt-get simulation needed — hold/unhold touch only selection state, not a transaction, so they bypass the collateral-guard machinery entirely.

**Three-way review:** falls out for free. Holds go through the ordinary checkbox `ReviewGroup` (not the collateral/unreproducible special flows). apply = overwrite source&gt;target (runs the apt-mark command), skip-once = `SKIP_ONCE`, skip-always = `SKIP_ALWAYS` → `_record_permanent_skips` writes the machine-local `DecisionFile` under manager `"apt"` keyed by `apt:hold:&lt;pkg&gt;` (`state.py`, `DECISION_FILE_RELPATH_TEMPLATE`). `filter_inert` (`sync_core.py:363-364`) then drops that hold item from future runs on the holding machine. All existing.

## 5. INTEGRATION HAZARD — coexistence with the HELD_OR_PINNED→REPORT_ONLY guard (the crux)

They are **orthogonal and must both stay**, but the current guard needs a scoping change to avoid a double-report and to stop swallowing the hold diff.

The concern: the two concepts live at different layers. The **package** item (`apt:package:&lt;pkg&gt;`) answers "should the package be installed / at what version" — and while it is held on the target, that answer must remain **REPORT_ONLY** (D-04: never force-downgrade/upgrade a package the user pinned in place; apt would refuse anyway). The **hold** item (`apt:hold:&lt;pkg&gt;`) answers a different question — "should the hold flag itself exist on the target". Converging the hold flag as its own item is correct and does not touch the package's install/version.

Concrete conflict to de-dupe: today a package held **on the source** and installed-but-not-held **on the target** would (once holds are proper diffs) produce *both* a `HELD_OR_PINNED` REPORT_ONLY on `apt:package:&lt;pkg&gt;` **and** an add-hold `apt:hold:&lt;pkg&gt;` item — the user sees the same package twice, once as an un-actionable report and once as the real actionable hold. That is redundant noise.

Recommended reshape of `_diff_apt_packages` (`sync_core.py:235-258`):
- **Split the fact stream by mechanism.** Pins stay exactly as they are: `HELD_OR_PINNED`/REPORT_ONLY is still the right presentation for a pin (a pin is a `preferences.d` *file*, already synced as an `AptPinItem` by `config`-style file diff — the REPORT_ONLY on the package is the informational echo). **Holds move out** of the `held_or_pinned` dict entirely and are diffed as `AptHoldItem`s.
- With holds removed from the guard, the `HELD_OR_PINNED` branch keys **only on pins**. A held-on-target package's install/version item then needs a *separate* suppression: keep a REPORT_ONLY (or simply suppress the package's install/version diff) when `target_item.name` is in the target's hold set, so a held package is never proposed for install/upgrade — but the *hold itself* is now carried by the `apt:hold:` item, not the `apt:package:` report. In other words: the hold set still suppresses package-level action on the target (its original job), but no longer masquerades as the review-worthy fact — the `apt:hold:` item is that fact.

**De-dupe rule, stated plainly:** for a given package name, the `apt:package:` item governs the package's presence/version (REPORT_ONLY while target-held), and the `apt:hold:` item governs the flag. They never both *act*; at most the package item reports and the hold item acts. To avoid showing the name twice in the review, suppress the package-level `HELD_OR_PINNED` **report** for the hold mechanism whenever an `apt:hold:` diff for the same name is being emitted (pins keep their report, since pins have no separate actionable item on the package axis — only the `AptPinItem` file).

**Ordering concern (real):** apply hold changes relative to installs matters.
- **Add-hold vs install:** if the same run both installs a package and holds it, the hold must be applied **after** the install (you cannot hold what dpkg has no record of, per §2's open question — and even if you can, holding first would make apt refuse the very install). But in practice a package needs *installing* only when absent on target, and a *hold* on it is only meaningful once present — so **hold after install**.
- **Remove-hold vs upgrade/change:** a target-held package whose hold the user wants removed must be **unheld before** any package-level change that the hold would block. Since package version changes are REPORT_ONLY today (never converged), this is not yet a live conflict — but if it ever becomes one, unhold must precede it.

This is the same "convergence order is an apt FACT" situation the repo group already handles via `_ITEM_CLASS_ORDER` and `plan()`'s stable sort (`apt_sync.py:102-107, 672-677`). Give `APT_HOLD` a rank that places **add-holds after packages** and **remove-holds before packages** — which, because add-hold and remove-hold would want opposite ranks, is the one wrinkle: either split them by action into two ranks, or (simpler) run all hold converges in a dedicated pass after package installs (add-holds are the common case; remove-hold-before-change is moot while versions are REPORT_ONLY). Recommend: rank holds **last** (after packages) for v1, documented as safe because the only package-level action that co-occurs is install, and hold-after-install is the correct order.

**Does `collect_hold_pin_facts` reading BOTH machines still make sense?** For **pins**, yes (unchanged — it reads the target's `preferences.d`). For **holds**, it should become a proper **source-vs-target diff** rather than a merged "either machine" fact list. The current "read from both, key on target" design is precisely what silently drops source-only holds (§1) and what would double-report. Split it: keep the pin read as a target-only fact for the REPORT_ONLY echo; convert the two `showhold` reads into source-hold-set and target-hold-set feeding the new `AptHoldItem` diff.

## 6. Pin case — holds are the only unreplicated apt block-mechanism

Confirmed. Pins are `/etc/apt/preferences.d/*` files, and those already travel as `AptPinItem`s via the whole-file-digest sync in `_plan_repo_diffs`/`_diff_apt_pins` (`apt_sync.py:712-747, 834-869`), converged by `_write_or_remove_repo_item` (D-13). apt's two block mechanisms are pins (preferences.d) and holds (dpkg selection); pins replicate today, holds do not. ### 2. ENUMERATE — `flatpak mask` CLI facts (verified live, Flatpak 1.14.6)

- **List:** `flatpak mask` with no patterns lists masks. Masks are **per-installation** (like remotes), so you must query each scope explicitly: `flatpak --user mask` and `flatpak --system mask`. Known upstream quirk: bare `flatpak mask` historically does not include `--user` masks ([flatpak#4216](https://github.com/flatpak/flatpak/issues/4216)), and the help shows `--system` is the **default** scope for this verb (unlike `flatpak list`) — another reason to always pass an explicit scope flag.
- **Output format (verified live):** one pattern per line, each prefixed with **two leading spaces**, no header, no scope column:
  ```
    org.broken.App
    org.domain.*
  ```
  Parsing = strip leading whitespace per non-blank line. Scope is known from the flag you passed, not parsed (identical to how `_parse_flatpak_remotes` takes scope as a param, :169).
- **Patterns, not exact refs:** a mask is a *partial ref* with `*` wildcards, e.g. `org.some.App`, `app/org.domain.*`, `org.some.App/arm`. Patterns contain `/` and `*` but **no `:`** (flatpak refs are `/`-separated), so the existing 3-colon `item_id` split (`_split_flatpak_item_id`, :126, `split(":", 3)`) stays exact for a `flatpak:mask:&lt;scope&gt;:&lt;pattern&gt;` id.

### 3. CONVERGE commands (verified live)

- Add: `flatpak --user mask &lt;pattern&gt;` / `flatpak --system mask &lt;pattern&gt;`
- Remove: `flatpak --user mask --remove &lt;pattern&gt;` / `flatpak --system mask --remove &lt;pattern&gt;`
- **Sudo:** system scope writes into `/var/lib/flatpak` → needs root; user scope needs none. Mirror the existing `_sudo_prefix(scope)` (:116) exactly — `sudo ` iff scope == "system".
- **Idempotency (verified live):**
  - Adding an already-present mask → **exit 0, no error** (idempotent). ✅
  - Removing a **non-existent** pattern → **exit 1**, `error: No current masked pattern matching &lt;p&gt;` (NOT idempotent). Not a problem here: converge only removes patterns the target-scope query actually reported, and `--remove` matches by exact listed pattern string.

### 4. DESIGN — proposed item model (mirrors the remote-per-scope analog)

New `ItemClass.FLATPAK_MASK = "flatpak_mask"` in `items.py`, plus a frozen `FlatpakMaskItem`:

- Fields: `pattern: str`, `scope: Literal["user","system"]`.
- `item_id` → `f"flatpak:mask:{self.scope}:{self.pattern}"` (scope-in-identity, same rationale as `FlatpakItem`/`FlatpakRemoteItem` at `items.py:400,426`).
- `label()` → e.g. `f"{pattern} mask ({scope})"`.

Capture/diff (add to `flatpak_sync.plan()`, mirroring the remotes path at :446-455):

- `_capture_all_source_masks()` / `_query_all_target_masks()` — one `flatpak {flag} mask` per scope, parsed like remotes.
- `_diff_flatpak_masks(source, target)`: a mask is a boolean membership per `item_id` (no "value" field to change, unlike a remote's URL), so **only two diff directions** — never a CHANGE:
  - source-has, target-lacks → `MISSING_ON_TARGET` / `DiffAction.INSTALL` → converge `flatpak {scope} mask &lt;pattern&gt;`.
  - target-has, source-lacks → `EXTRA_ON_TARGET` / `DiffAction.REMOVE` → converge `flatpak {scope} mask --remove &lt;pattern&gt;`.
  - present both sides (same scope+pattern) → no diff.

This drops cleanly into the existing pipeline with **no changes to review.py or `_build_review_groups`**: `INSTALL`→default-checked install group, `REMOVE`→its own removal group (unchecked), and the three-way apply / skip-once / skip-always flow is inherited unchanged. One small addition: an `_ACTION_VOCABULARY` entry `(ItemClass.FLATPAK_MASK, DiffAction.INSTALL): "mask"` and `(…, DiffAction.REMOVE): "unmask"` (`sync_core.py:113`) so the review reads "Mask …" / "Unmask …" instead of the raw "install"/"remove" fallback. `converge()` gains a `FLATPAK_MASK` branch delegating to a new `_converge_mask(diff)` (parse scope+pattern via `_split_flatpak_item_id(id, "mask")`, `sudo` via `_sudo_prefix`, `shlex.quote` the pattern). No source-side lookup dict needed (unlike refs/remotes) — the pattern is fully recoverable from `item_id`, so no `_source_masks_by_id` cache is required.

### 5. INTEGRATION / ordering

- Masks are patterns independent of whether a matching ref is installed, so they carry **no hard ordering dependency** on ref/remote convergence the way a ref depends on its remote (D-14). They can be appended to `plan()`'s `diffs` tuple after the ref diffs.
- **Real interaction (partially verified):** a mask blocks *automatic* update/installation of matching refs (incl. auto-pulled extensions/dependencies), per Flatpak docs — it does **not** short-circuit an explicit `flatpak install` at the pre-remote stage (verified live: an explicit install of a masked ref proceeded to the remote-summary fetch and failed there on the remote, not on the mask). Practical guidance: if the same run both installs a ref AND adds a mask that could match it or its extensions, **install refs first, apply masks last**, so a mask can't suppress an auto-pulled dependency of a ref we're installing in the same run. Concretely: order `diffs` as remotes → refs → masks.

### 6. SUDO / scope-validation implication

Adding system-scope masks **does** widen `validate()`'s sudo trigger. `_system_scope_in_play()` (`flatpak_sync.py:563`) currently returns True only for system-scope refs/remotes; it must also return True when a **system-scope mask exists on either machine** (add `if await self._query_target_masks("system"): return True` and the source equivalent). `flatpak --system mask` writes to `/var/lib/flatpak`, so it requires passwordless target sudo just like system install/remote-add — the existing `sudo -n true` gate (:610) and `_TARGET_SUDO_COMMANDS = ("/usr/bin/flatpak",)` (:96) already cover the binary; only the "is system scope in play" predicate needs the extra check. A run with only **user-scope** masks stays root-free.

## Report: Design for replicating per-snap hold state (issue #208)

### 1. THE CRUX — two independent mechanisms, separate storage/namespaces

There are two distinct "hold" mechanisms, and #208's per-snap work can safely coexist with the sync-window hold the orchestrator just added:

| | (a) Sync-window hold (orchestrator) | (b) Per-snap hold (#208) |
|---|---|---|
| Command | `sudo snap set system refresh.hold=&lt;RFC3339&gt;` | `sudo snap refresh --hold[=forever\|&lt;dur&gt;] &lt;snap&gt;` |
| Namespace | system **config option** | per-snap **snapstate** |
| Read via | `snap get system refresh.hold` → timestamp or `forever`; also `snap refresh --time` "hold:" line | `snap list &lt;snap&gt;` → `held` in **Notes** column |
| Scope | all snaps, **auto-refresh only** (does NOT block explicit `snap refresh &lt;snap&gt;`) | that snap's auto-refresh + general `snap refresh`; explicit `snap refresh &lt;snap&gt;` still bypasses |

Verified facts:
- Per-snap holds are stored/queried **separately** from `snap set system refresh.hold`. The snapcraft "Manage updates" doc states per-snap holds via `snap refresh --hold &lt;snap&gt;` are separate from the system-wide `refresh.hold` option; held snaps surface as `held` in `snap list` Notes, the system option surfaces via `snap get system refresh.hold` / `snap refresh --time`.
- A per-snap hold does **NOT** appear in `snap get system refresh.hold` (that query returns only the config option's value — confirmed by the orchestrator's own read at `orchestrator.py:1279-1288` and `snap_sync.py:452-455`, both treating it as a single system value).
- Setting `refresh.hold` during the sync does **NOT** clobber per-snap holds — different namespace. This is exactly what the author already asserted in-code at `orchestrator.py:1337-1339`: restore "set[s] `refresh.hold` empty … leaving any unrelated per-snap holds untouched." The orchestrator restores via `snap set system refresh.hold=""` (config namespace), never `snap refresh --unhold` (which WOULD touch per-snap holds). So convergence in (b) survives cleanup.

One item genuinely needing empirical confirmation (label: inferred, not doc-verified): whether setting the **config option** `refresh.hold=&lt;timestamp&gt;` causes individual snaps to render `held` in `snap list` Notes. Reasoning strongly says NO — the `held` note derives from per-snap snapstate, and the docs only ever tie `held`-in-Notes to `snap refresh --hold &lt;snap&gt;` — but no doc states it explicitly, and it matters because snap_sync's capture (`snap list --all`) runs *inside* the sync window, i.e. after the orchestrator engaged the system hold (`_hold_snap_autorefresh` runs before jobs). Test to confirm on a real machine: `sudo snap set system refresh.hold="$(date -d '+1 hour' -Iseconds)"; snap list | grep held` — expect no snap flipped to `held`. If it DID, per-snap capture would need to run before the sync-window hold is engaged.

### 2. Enumerate per-snap holds

- Read command: `snap list --all` (already used) — the **Notes** column contains `held` for a per-snap-held snap. Example line: `yt-dlp 18 212 latest/edge morrisong held`.
- The existing parser already reads the Notes column: `snap_sync.py:104-121` indexes `Notes` and splits on `,` (`if "disabled" in fields[notes_idx].split(",")`). Extending it to also detect `held` is a one-line addition — no new command, no extra round-trip.
- Expiry/`forever` distinction: `snap list` Notes shows only the boolean `held`, not the expiry. Per-snap detail (until-when) would need `snap refresh --time` or the API; for #208's purpose (replicating the user's *deliberate indefinite* hold) the boolean is sufficient.

### 3. Converge commands (per-snap)

- Hold indefinitely: `sudo snap refresh --hold=forever &lt;snap&gt;` (doc-confirmed). Bare `snap refresh --hold &lt;snap&gt;` also holds, but the **`--hold=forever` form is explicit and safe** — critically, never emit bare `snap refresh --hold` with NO snap name (that is the mutating global-hold pitfall in `snap_sync.py:4-13`).

- Duration: **not relevant to #208** — replicate only the user's deliberate indefinite hold. Use `--hold=forever` / `--unhold`. (Time-boxed holds would drift/expire and aren't a stable state worth replicating.)
- Requires the snap **installed** on the target — you cannot hold an absent snap.

### 4. Proposed item model + diff + converge

Item identity (new, distinct from the presence item `snap:&lt;name&gt;`):
- `item_id = "snap:hold:&lt;name&gt;"` — a separate id so it flows through the diff/review/DecisionFile pipeline as its own reviewable item, independent of the snap's install/revision diff.
- Add a `held: bool` field to the frozen `SnapItem` (`items.py:356-379`), populated by `_parse_snap_list`. Diff (a second pass in `_diff_snap_items`, emitted **after** the presence diffs):
- source-held ∧ ¬target-held → converge = **hold** on target.
- target-held ∧ ¬source-held → converge = **unhold** on target.
- both-held or neither-held → no diff.
- Only emit a hold diff when the snap is present on the source (source is authoritative for the desired state).

Converge: `SnapSyncJob.converge` (`snap_sync.py:324-347`) currently dispatches on `diff.action`. A hold item must be routed by **item_id prefix** (`snap:hold:`), not action, so it doesn't collide with the revision/channel `CHANGE` branch. Command per direction as in §3.

### 5. Integration / ordering — and the design question

Ordering (verified): `apply()` builds `apply_diffs` by filtering `plan.diffs` **in original order** (`sync_core.py:438-442`) — it does NOT re-sort by the review-group order. So if `_diff_snap_items` emits all presence diffs (install/change/remove) first and all `snap:hold:*` diffs second, then within snap_sync's own `apply()` **install always lands before its hold** for the same snap. Good.

Cross-job ordering is fine too: snap_sync runs as one sequential job; the hold operates on the same target `snap` the install just created, all inside snap_sync.

Edge case to handle: if the user APPLYs a `snap:hold:&lt;foo&gt;` but SKIPs the `snap:&lt;foo&gt;` install, the hold command hits an absent snap and fails (a tolerable per-item D-27 failure, but noisy). No conflict with the sync-window system hold: cleanup restores via `snap set system refresh.hold=""` (config namespace, `orchestrator.py:1333-1344`) — it never runs `snap refresh --unhold`, so a per-snap hold converged during the job is untouched by cleanup. Confirmed by the author's own code comment.

Genuine design question for a human — the review verb / direction:
The task proposes a single `DiffAction.CHANGE` for holds. But hold and unhold are **opposite directions**, and the review pipeline groups purely by `DiffAction` and default-checks by direction (`sync_core.py:308-343`, `review.py:92,424-431`). Under one `CHANGE`:
- hold and unhold land in the *same* group, both default-**checked**, both labeled "change" (no vocabulary entry for `(SNAP, CHANGE)`, so `_ACTION_VOCABULARY` at `sync_core.py:113-120` falls back to `"change"`), and mixed in with same-revision retracks.
- That violates the spirit of D-07 ("removal-direction in its own group, unchecked") for an *unhold*, which removes a protection the user deliberately set on the target.

Two options to resolve — recommend deciding before planning:
- (A) Keep `DiffAction.CHANGE`, converge inspects direction. Simplest, but review can't visually distinguish hold vs unhold and unhold is default-checked.
- (B, recommended) Add `ItemClass.SNAP_HOLD` and map **hold → `DiffAction.INSTALL`-direction**, **unhold → `DiffAction.REMOVE`-direction**, with `_ACTION_VOCABULARY` entries `(SNAP_HOLD, INSTALL)→"hold"`, `(SNAP_HOLD, REMOVE)→"unhold"`. This puts unhold in its own removal group (unchecked by default) and gives correct review verbs, at the cost of two small enum/vocabulary additions.
