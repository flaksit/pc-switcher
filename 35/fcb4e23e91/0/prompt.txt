<result>## Verdict: (b) — the hold IS applied; the read-back is what's broken

`snap get system refresh.hold` requires admin auth. Run as an unprivileged user it does not return "empty" — it **fails with `access denied (try with sudo)`** and prints nothing to stdout. `_capture_snap_hold` therefore returns `None` on every run, on every machine, unconditionally.

Environment: pc2, Ubuntu 24.04, **snapd/snap 2.76.1**.

### Evidence

Baseline (no hold set), as `testuser`:

```
$ snap get system refresh.hold          rc=1  stdout=[]  stderr=[error: access denied (try with sudo)]
$ sudo snap get system refresh.hold     rc=0  stdout=[]
  state.json core.config.refresh = {"hold": ""}
```

The exact orchestrator command, then read-back three ways:

```
$ sudo snap set system refresh.hold="$(date -u -d '+6 hours' +%Y-%m-%dT%H:%M:%SZ)"   rc=0
$ snap get system refresh.hold          rc=1  stdout=[]  stderr=[error: access denied (try with sudo)]
$ sudo snap get system refresh.hold     rc=0  stdout=[2026-07-26T15:50:19Z]
  state.json core.config.refresh = {"hold": "2026-07-26T15:50:19Z"}
$ snap refresh --time                   (no sudo)
  timer: 00:00~24:00/4
  last: today at 11:47 CEST
  hold: today at 17:50 CEST
  next: today at 13:14 CEST (but held)
```

snapd authoritatively reports the hold in force (`hold:` line, `next: ... (but held)`), and it persists in `/var/lib/snapd/state.json`. **The pause works.** The per-snap `hello` hold from the CI run is irrelevant — my baseline had no per-snap hold and the read failed identically.

### Consequence in production (the real bug)

`orchestrator.py:1317` (`_capture_snap_hold`) always returns `None` → `_hold_snap_autorefresh` records "no prior hold" on both hosts → `_restore_snap_hold` takes the `prior is None` branch and runs `sudo snap set system refresh.hold=""` on **both** machines in `_cleanup`. Any hold the user set themselves (`snap refresh --hold`, an admin-set `refresh.hold`, incl. `forever`) is silently destroyed by every sync. Nothing warns: the `snap set` exits 0, and the failing `snap get` is swallowed by `result.success and value`.

Same defect, informational only, at `src/pcswitcher/jobs/snap_sync.py:667-670` — validate() logs `snap refresh.hold: (none)` for both hosts on every run regardless of actual state.

The CI failure is the same root cause in the test helper: `tests/integration/jobs/test_package_sync.py:601-607` `_capture_system_refresh_hold` also omits sudo, so `assert engaged is not None` can never pass. Its `_restore_system_refresh_hold` mirrors the destructive `refresh.hold=""` write.

### Documented rule / mechanism (sources)

- Access control: snapd `daemon/api_snap_conf.go:39-45` — `/v2/snaps/{name}/conf` has `ReadAccess: authenticatedAccess{Polkit: polkitActionManageConfiguration}`. The shipped policy (`/usr/share/polkit-1/actions/io.snapcraft.snapd.policy` on pc2, identical to snapd `data/polkit/io.snapcraft.snapd.policy`) sets `io.snapcraft.snapd.manage-configuration` to `allow_any=auth_admin`, `allow_inactive=auth_admin`, `allow_active=auth_admin_keep`. **Reading** snap config is admin-gated in every case — so this is not an SSH artifact: on a real desktop seat it would raise an interactive polkit prompt a non-interactive sync cannot satisfy.
- `system` is an alias for `core`: verified — `sudo snap set core refresh.hold=&lt;ts&gt;` is read back identically by `sudo snap get system refresh.hold`. No historic distinction remains at 2.76.1.
- snapd only clears `refresh.hold` when it has **expired** (`overlord/snapstate/autorefresh.go`: `clearRefreshHold()` called from `Ensure()` in the "expired hold case" branch). It does not clear or reject an in-future hold.
- Format: `configcore/refresh.go:81-89` — value must be RFC3339 or the literal `forever`, else `snap set` errors out. The orchestrator's `+%Y-%m-%dT%H:%M:%SZ` is accepted.
- No cap at set time: `+200 days` was stored and reported verbatim (`hold: 2027-02-11`). `maxPostponement = 95 * 24h` (`autorefresh.go:53`) constrains gating-snap holds (`autorefresh_gating.go:474-475` explicitly exempts `holdingSnap == "system"`), not the general config option. A 6-hour hold is nowhere near any limit.

## `_restore_snap_hold` guard: implemented

A failed capture is no longer treated as "there was no hold" — the clear is skipped and a WARNING is logged. Rationale, recorded in the docstring: the two error directions are not comparable. Clearing an option whose pre-sync value is unknown permanently destroys a hold the user may have set (`forever` has no expiry to fall back on); skipping the clear leaves at worst the timed 6-hour hold this run set, which self-expires — the same crash backstop the mechanism already relies on. Also note the correlated case: if the capture failed for lack of privilege, the apply almost certainly failed too, so there is usually nothing of ours to clear anyway.
