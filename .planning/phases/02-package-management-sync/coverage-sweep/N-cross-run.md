## Gaps

**N3 — target-held mark, role-reversed second run.** Two halves are asserted separately and neither by a two-cycle run: `test_skip_always_on_remove_writes_to_target_not_source` proves a `REMOVE` decision writes on the target, using a hand-built `PackagePlan` and no `plan()` at all; `test_target_held_inert_item_absent_even_though_source_also_differs` proves the inertness by feeding a hand-written decision file as the target's `cat` response. Nothing records-then-replays for a plain package item, and nothing runs the reversed direction where the mark's holder becomes the source (`steam` then diffs as `INSTALL`, so `_drop_inert_diffs` looks it up in the *source* file — the opposite branch of `_decision_holder_is_source`). Closable with mocks: extend `test_block_state_decisions.record_skip_always` to `AptSyncJob` with an `apt:package:` item and a target-only manifest, then replay the recorded file (a) with the same roles and (b) with source/target manifests swapped. A VM version would be the mirror of `TestPackageSyncWholeRunContracts::test_skip_always_is_inert_in_both_roles` starting from a target-only package.

**N7 — "run 1 recorded nothing" for an explicit skip-once.** `test_install_propagates_then_reversed_removal_needs_approval` genuinely answers `SKIP_ONCE` in run 2 and gets the same item back in run 3, so "offered again, unchanged" is VM-proven. Nothing asserts that the `SKIP_ONCE` run left no `DecisionEntry`: `_record_permanent_skips` filters on `decisions.get(...) != Decision.SKIP_ALWAYS`, and the only no-write tests (`test_package_state`:`TestPipelineWiring::test_no_record_call_when_dry_run`, `::test_no_record_call_when_outcome_was_not_interactive`) both use `SKIP_ALWAYS` and guard the other two conditions. Closable with mocks: a `TestPipelineWiring` sibling deciding `SKIP_ONCE` on an interactive, non-dry-run outcome and asserting no `mv --force` on either executor.

**N11 — the second run, and "the repository stays" as state.** The three unit tests assert only the log record: `_STRANDED_FOO` present, at INFO, with no `WARNING`-or-above anywhere, and the negative control that a repository a surviving install still needs is not named. Two things are unasserted: (a) that the file is still on the target when the run ends — nothing checks the absence of a delete/rollback of `foo.sources` in `all_calls(target)`; (b) run 2, where both machines have the file, so `diff_apt_sources` produces no `extra` entry and the deletion is never offered. (a) is closable with mocks in `TestARepositoryWrittenForADeclinedInstall` (assert no `rm`/restore naming `sources.list.d/foo.sources` after the withdrawal). (b) is closable with mocks too — a second `AptSyncJob(plan())` whose source and target digests both carry `foo.sources` — but a VM version is worth having, since the withdrawal path only exists after a real `apt-get --dry-run install` drift.

**N12 — code contradicts `PKG-FR-REPO-DELETE`.** The article says usage is "counted after this run's approved removals". `job.py` builds `going` from every `APT_PACKAGE` diff whose action is `REMOVE` — the *proposed* removals, at plan time, before any answer exists — and `diff_apt_sources` withholds on that `in_use` set. So `S` is raised as a removal item the moment `R` becomes a removal candidate, whatever the user then answers, and nothing re-checks at converge: `etc_apt.converge_item` → `ensure_converged` → `approved_diffs` filters on the repository's own decision only. Approving `S` while declining `R` therefore deletes the repository out from under an installed package. `flatpak_sync` does not have this bug — it counts after the converge loop against the target's real state (`test_flatpak_sync`:`TestUnusedRemoteIsDeleted::test_a_removal_the_user_declined_keeps_the_remote`, `::test_a_removal_that_failed_keeps_the_remote`), which is the shape apt is missing. Fixing it is a code change, not a test gap; the regression test is a mocked one (source with nothing, target with `vendor.list` + `vendor-tool`, decisions `{apt:package:vendor-tool: SKIP_ONCE, apt:source:vendor.list: APPLY}`, assert no `rm` of `vendor.list`). No VM needed.

**N16 — the round trip.** `test_auto_installed_dependency_produces_no_diff_of_any_kind` proves the manifest is `apt-mark showmanual` only, so an auto-installed `Q` is never an item in *one* run, with a mocked executor. Nothing follows a real dependency across an install-then-remove round trip, which is the only way to see what the target's own apt does to `Q` between the two runs (`apt-get remove`, never `autoremove`, so `Q` should survive `P`'s removal and still never be proposed). Needs a VM — the claim is about real dpkg/apt dependency bookkeeping, not about pc-switcher's diff. Build it on `TestCrossDirectionRoundTrips::test_install_propagates_then_reversed_removal_needs_approval`: pick a candidate with a non-manual dependency, capture `dpkg-query` state on both machines before run 1 and after each run, and assert `Q` appears in no `apt-get install`/`apt-get remove` argument list and in no review line.

**N17 — the guard is never reached by a run.** All six `TestSnippetRegistryOverwriteGuard` tests call `job._push_snippet_registry()` directly with the target's registry hand-fed as a `cat` response; the prompt, the named entry (`cnpg`), the `allow=False`, the `SyncAbortedByUser` and `send_file` not called are all asserted. Unasserted: that a run 1 which authors a snippet actually leaves the other machine holding an entry the next run's source lacks, and that the abort ends the *run* (the test asserts the exception, not the sync's exit code or that later jobs did not run). Closable with mocks for the reach-the-guard half (`execute()` with a divergent target registry, assert the confirmer was consulted from inside the run). The end-to-end version needs a VM: `TestManualInstallsSyncEndToEnd::test_manual_installs_sync_pushes_registry_and_replays_snippet` already leaves both registries on disk — author a second entry on pc2 only, run pc1→pc2 again non-interactively, assert the run aborts and pc2's registry is byte-identical.

**N19 — the key, and the second run.** `test_the_count_runs_after_this_runs_approved_removals` proves the same-run sequencing (uninstall issued, then `flatpak remote-delete --user customremote`) and `test_a_remote_nothing_uses_is_deleted_and_never_offered` proves `plan.groups == ()`. Unasserted: `PKG-FR-FLATPAK-REMOTE-DELETE`'s "Deleting a remote MUST take its signing key with it" — no test looks at the keyring after a deletion — and the run-2 emptiness. The key half needs a VM: whether `flatpak remote-delete` removes `<remote>.trustedkeys.gpg` is flatpak's own behaviour, asserted nowhere and only recorded as a live measurement in `test_package_sync`'s `test_flatpak_derives_the_remote_its_ref_needs_and_carries_its_key` docstring. Add it to a VM test that deletes the fixture remote through a sync and then checks `~/.local/share/flatpak/repo/<remote>.trustedkeys.gpg` is gone. The run-2 half is mocks-only work (a second `plan()` over the post-deletion state).

**N21 — the composition across two jobs.** `test_excludes_old_revisions_keeps_current_common_and_current_symlink` proves `snap_sync_exclude_paths()` keeps the `current`-resolved revision dir and excludes the retained old ones, against a `tmp_path` fake home; `test_snap_sync_enabled_includes_revision_exclusion` proves `folder_sync` puts those paths in the rsync command when `snap_sync` is enabled. Unasserted: that `snap_sync` converges the target's revision *before* `folder_sync` computes the set (the whole premise of the design comment in `snap_sync_exclude_paths`), and that the data therefore lands at a path the target's snapd reads. Needs a VM, both jobs enabled in one run: diverge the fixture snap's revision on pc2, write a marker file into pc1's `~/snap/<app>/current/`, run `apt`-free `snap_sync`+`folder_sync`, then assert pc2's `~/snap/<app>/<source revision>/` holds the marker and pc2's `current` resolves to that same revision.

**N22 — hand check.** No automated test spans it. The nearest pieces are `TestPackageSyncWholeRunContracts::test_each_manager_reviews_before_its_own_mutation` (two jobs, apt + snap, review-before-own-mutation by end state), `TestPackageSyncWholeRunContracts::test_continue_on_item_failure` (non-zero exit from a failed item inside one job) and `test_package_sync_core`:`TestOrchestratorPackageItemFailuresContinuation::test_failing_package_job_does_not_cancel_remaining_jobs` (mocked). Nothing runs all four jobs together, and the row's value is a reviewer watching one real run end to end — keep it as the hand-validation row rather than converting it into a VM test, which would be a slow duplicate of the three above.

## Notes for the assembler

Rows here must not restate a single-run branch. Where a narrative's only new content is "and it still works the second time", it belongs in N only if a requirement makes the second run's outcome different from the first's.

Three rows are not genuinely cross-run and could move to another area — I marked them on their own merits rather than downgrading them for the framing:

- N10 is a single run. Its whole expectation (one question, and key→source→`apt-get update`→install ordering, with the pin before the sources) is asserted in two adjacent apt tests. It belongs in the apt repositories/keys area.
- N15's "arrives on Vega as an automatic dependency" and "a later run" are flavour: the branch is "manual on the source, auto on the target ⇒ not protected from collateral", which is asserted directly. It belongs in the apt collateral area.
- N20's "in any run" is a property of the decision file's persistence (N1/N3's territory), not a second run; the row's own content is the usage count including marked apps, which is asserted single-run.

Two rows overlap other areas and their `V` marks should not be double-counted: N13's key half is the same VM test as the apt-keys area's `PKG-FR-KEY-CLEANUP` row, and N18's skip arm is the same VM test as the ESM-gate area's `PKG-FR-ESM-SKIP-WHOLE-JOB` row.

N18's two arms live in different tests — the skip arm on VMs, the attached arm only as a unit test with a mocked `pro` probe. No test runs both in sequence, and the attached arm cannot be put on CI VMs: `pro attach` needs the user's own subscription token, which the project's secrets rule keeps out of CI. That is a fixture limit, not a coverage hole to schedule.

N12 is the one finding in this sweep. It is a code/requirement conflict rather than a missing test, and it is worth surfacing to whoever assembles the apt repositories section, where `PKG-FR-REPO-DELETE` also has single-run rows that will read as green.
