## Scope decision: machine-specific packages only

This is the judgement call you asked me to make explicitly, and it is a genuine trade-off — the invisibility argument alone does not settle it. An ordinary package installed identically on both machines from the removed repo is *equally* invisible today. Three things decided it:

1. **Machine-specific is invisible structurally, not incidentally.** `filter_inert` guarantees a skip-always package produces no `ItemDiff` in any run, forever. An ordinary package's silence is a coincidence of this run's state; it remains eligible for its own removal diff.
2. **Skip-always is an explicit promise** — "this machine keeps this, syncs never touch it". Pulling its repo out from under it breaks that promise specifically. No equivalent promise exists for ordinary packages.
3. **Measured, not assumed:** widening makes the detail's length a property of the machine. On this box `ubuntu.sources` maps to 126 manual packages. A review line naming 126 packages informs nobody. Cost was *not* the deciding factor — I measured `apt-cache policy` over all 153 manual packages at 71 KB / 0.5 s, which is affordable. Readability was.

The limitation is documented in `docs/jobs/package-sync.md` and in a new "Accepted scope limits" section of the matrix, not left implicit.

- **`/usr/share/keyrings` is not captured.** `dpkg -S` confirms `google-chrome.gpg`, `hashicorp-archive-keyring.gpg`, `nodesource.gpg`, `claude-desktop.gpg`, `task-task-archive-keyring.gpg` are **owned by no package** — the user placed them by hand. They are exactly as machine-local as an `/etc/apt/keyrings` key, and nothing replicates them. (`ubuntu-archive-keyring.gpg` and `tailscale-archive-keyring.gpg` *are* package-owned, so for those "dangling" is a false alarm of a different kind: the key arrives with its own deb.) `_keyring_local_path` (`apt_sync.py:1867-1877`) already contemplates "a package-owned keyring under `/usr/share/keyrings`, say, which the target's own packages provide" and returns `None` — it directly contradicts `_dangling_keyring_ref`, which calls the same reference fatal.
- **Inline-armored `Signed-By:` is mis-parsed.** `_parse_source_file`'s docstring (`apt_sync.py:274-281`) asserts that with an inline key "the field value is empty and the armored block follows on continuation lines… That yields NO ref." **That assertion is false** for files written by Ubuntu's `add-apt-repository`: verified, `git-core-ubuntu-ppa-noble.sources:5` reads literally `Signed-By: -----BEGIN PGP PUBLIC KEY BLOCK-----`. `^Signed-By:\s*(?P&lt;path&gt;\S+)` captures `-----BEGIN` as a path, which is then reported as a dangling keyring. Every PPA added the normal way is affected.

User-visible outcome: on a first sync to a fresh machine, ~2/3 of the user's repositories appear in the review as unactionable report lines, are never written, and the dozens of packages behind them are simultaneously offered as default-ticked installs that then fail with `E: Unable to locate package`. This *is* the user's stated scenario failing, just via a different mechanism than the one hypothesised.

This sits inside the blast radius of the in-flight rewrite — **re-verify against the finished diff before filing.**

## F2 — HIGH. Skip-always on a source file makes its packages fail forever, silently

A source `INSTALL` diff is source-held under D-08a (`sync_core.py:406-415`), so skip-always records on the source and `_drop_inert_diffs` removes the diff on every subsequent run (`sync_core.py:417-445`, applied to apt's own repo diffs at `apt_sync.py:823-829`). The packages from that repo keep their own `apt:package:&lt;name&gt;` identities and keep being emitted as default-ticked installs — **every run, failing every run**, with an apt error that never mentions the declined repository. Nothing in the review, the failure text, or the decision file links the two. This is the "user unticked the source" case in its most durable form, and it is created by a legitimate, documented user action.

## F3 — MEDIUM. Package install approved, source unticked in the same run

Same defect, one run deep. Install groups default-ticked, sources and packages are two independent entries; unticking the source and leaving its packages ticked (the natural reading of "I don't want that repo *file*") produces one opaque per-item failure per package. D-27 makes this non-fatal and reported, which is the acceptable part; the unacceptable part is that the review never disclosed the dependency and the failure text does not name the cause.

## F4 — LOW/MEDIUM. Plan-time availability is computed against lists the code itself refuses to install against

`collect_unavailable_item_ids` (`apt_sync.py:770-783`) is the sole availability probe (verified: one call site, `sync_core.py:528`; no re-evaluation anywhere after the repo group converges). It runs before any `apt-get update`. Meanwhile ADR-020's Implementation Rules and `_ensure_metadata_refreshed` (`apt_sync.py:1355-1387`) both state that installing against stale lists is unsafe and force exactly one refresh before the first install. So the classification input is the state the apply path treats as untrustworthy. Because unknown names produce empty output (§1), the practical failure mode is benign — stale lists push packages *toward* being offered, not away. It is a documented-intent contradiction worth closing rather than a live incident.

## F5 — LOW. Source removal approved **and** a package from it approved for install, same run

Both diffs are producible simultaneously (the package needs a target-side candidate, which the doomed repo supplies). `_ITEM_CLASS_ORDER` puts `APT_SOURCE` at rank 2 and packages at rank 3 with the group's `apt-get update` between them, so the repo is deleted and the lists refreshed *before* the install runs. Result: guaranteed per-item install failure, no disclosure at review time, no guard at apply time. Removal groups are unticked by default (`review.py:499`), so this requires two deliberate ticks. Acceptable outcome, undisclosed cause.

## F6 — LOW. A pin the run is about to delete still suppresses its packages' diffs

`collect_hold_pin_facts` (`apt_sync.py:730-756`) reads the **target's current** `/etc/apt/preferences.d` at plan time. The pinned branch in `_diff_apt_packages` fires first and unconditionally (`sync_core.py:312-322`), emitting `HELD_OR_PINNED`/`REPORT_ONLY` and suppressing that package's own install/change/remove diff. So approving deletion of a pin file (rank 1, converges first) does not make the packages it governed reviewable in the same run — they reappear next run. Same plan-time-staleness shape as the hypothesis in §1, and here it is real. Self-healing, hence LOW.

The converse (a pin arriving this run, unknown to the target's plan-time facts) is harmless: pins converge at rank 1, so the install honours the new pin. If the user unticks the pin and ticks the package, the package installs unpinned — permitted by D-04's float policy, reported as `VERSION_MISMATCH` next run.

## F7 — LOW, but see §4. Pinning a package on the target makes it un-removable, silently and unfixably

The pinned branch requires only `target_item is not None` (`sync_core.py:312`). A package installed on the target but absent from the source, named by any target pin file, therefore never produces an `EXTRA_ON_TARGET`/`REMOVE` item — it is reported and nothing else. And because `REPORT_ONLY` items are denied skip-always, the user cannot mark it machine-specific to stop the noise either. ADR-020's #208 amendment justifies the echo as informational ("a pin can still permit an upgrade"); suppressing the *removal* direction is a stronger effect than any decision describes.

## F8 — LOW. Multi-name `Package:` stanzas lose all but the first name in the pin echo

`collect_hold_pin_facts`'s awk prints `$2` only (`apt_sync.py:748`). `Package: foo bar` yields a fact for `foo` alone; `bar` gets no echo and is diffed normally. `_parse_pin_file` (`apt_sync.py:344-356`) parses the same line correctly and its docstring acknowledges the divergence. Also, `Package: *` (very common) yields a fact for the literal `*`, matching nothing. Errs toward *fewer* suppressions, so it is a consistency wart, not a hazard.

## F9 — LOW. flatpak's twin of F5

`_remote_ready_on_target` (`flatpak_sync.py:1046-1054`) answers from the **plan-time** `_target_remotes_by_id` plus remotes added this run. A remote whose `REMOVE` is approved is still "present" by that test, and remotes converge before refs — so an approved remote deletion plus an approved ref install from it slips the guard and fails inside flatpak. Same contradictory-pair hole, milder because flatpak's own error is legible.

## F10 — Doc drift, not a bug. C26's key half

`_source_removal_details` (`apt_sync.py:925-983`, from `43a52fa3`) covers the removal side adequately **within its stated scope**: it names only packages recorded skip-always on the target (`apt_sync.py:961-963`), gated on a removal actually being offered, and it disclosed rather than refuses. There is **no apply-time guard**, and none is needed — deleting a source file destroys nothing, packages merely stop updating. The scope limit is deliberate and documented (`02-SCENARIO-COVERAGE.md` "Accepted scope limits"). But the in-flight rewrite drops keys as items, and the new docstring already says "a signing key is never offered for deletion" (`apt_sync.py:945-947`), while `docs/jobs/package-sync.md:135` and matrix row C26 still describe the key-removal detail. The other agent should carry that.

# 3. What existing machinery already mitigates

- **D-27 continue-and-report** covers F3, F5, F9 in the sense that matters: nothing is left half-applied, the run visibly fails, the remaining items proceed. What it does not do is *explain* — the failure text is apt's, and it never names the declined/removed repository. That is the whole gap for these three.
- **Removal groups unticked by default** (`review.py:100`, `499`) makes F5 and F9 require deliberate double-ticks. Real mitigation.
- **`_require_keyrings_ready`** (`apt_sync.py:1834+` region) guards key-before-source *inside* the repo group; it has nothing to say about packages, so it does not touch this family.
- **D-30 collateral classification** is the architectural precedent, not a mitigation: it proves plan-time classification of a cross-item consequence into its own review item is the house style.
- **Transactional repo group with rollback** (`apt_sync.py:1520-1660`) protects `/etc/apt` from a failed refresh. It does not roll back or re-plan packages — `test_rollback_does_not_prevent_package_items_from_being_attempted` (matrix C22) confirms packages are still attempted after a rollback, which means a rolled-back repo group leaves the F3 shape behind by design.
- **flatpak's `_remote_ready_on_target`** is the only existing dependency guard of this family anywhere in the phase, and it is apply-time refusal with a named per-item failure (`flatpak_sync.py:932-937`). apt has no counterpart.

Explicitly **acceptable as designed**: F10's scope limit; the "unticked pin + ticked package installs unpinned" case (D-04); D-27's per-item failure *as an outcome*.

# 4. Recommended design

Take the three candidate approaches in turn.

**Re-evaluating availability after the repo group converges — reject.** It would mean a second review (packages that only became available after the repos landed cannot be silently installed without one) and it breaks D-24's "each job reviews once before its own first mutating command". Cost far exceeds the benefit, and §1 shows the availability check is not where the damage is.

**Attempt the install and let D-27 report — keep, as the floor, but make it speak.** For F3, F5 and F9 this is genuinely the right outcome: the user made two contradictory ticks, one run, clear failure, next run shows the drift. The fix is one line of provenance in the failure text, not a guard.

**Teach plan time about repos in play — adopt, in the cheap direction only.** Do *not* ask the source which repo provides each package (that is a per-package `apt-cache policy` on the source and a URI-matching layer, for a benefit §1 shows is small). Instead reuse machinery `43a52fa3` already built: `_parse_source_file` already extracts each source file's URIs, and `_installed_origins_by_package` (`apt_sync.py:303-341`) already maps a package to its installed version's origin URIs from one batched `apt-cache policy`. Run that same batched policy **on the source** over the missing-on-target package names, match each package's origin URIs against the URIs of the source files this run is proposing to add/change/remove, and you have the package→source edge for free, at plan time, without a second review.

Concretely, per scenario:

# 5. Requirements gaps — need a user decision, not a fix

1. **What a `Signed-By: /usr/share/keyrings/...` reference means.** D-12 says "a repo's signing key travels bundled with its repo item, byte-for-byte" and names `/etc/apt/keyrings` and legacy `/etc/apt/trusted.gpg.d` as the key populations. `/usr/share/keyrings` is named nowhere in ADR-020 or 02-CONTEXT.md, yet it holds the keys for 9 of this machine's 16 repositories, 5 of them owned by no package. Nobody ever decided whether pc-switcher replicates them, ignores them, or treats their repos as unreplicable. (F1(b).)
2. **Whether a pin may block a removal.** D-05 and the #208 amendment describe pins as replicating constraints and as an informational echo on the package. Neither says a pin on the target should make a package un-removable *and* un-markable. (F7.)
3. **Whether declining a repository should imply declining its packages.** D-07 gives every item an independent three-way decision and says nothing about dependent pairs; N6 in the coverage matrix already records the mirror-image omission ("no 'this was the last package from that source, remove it too?' prompt — that requirement is not implemented"). My F2/F3 recommendation (disclose, still offer) is the option most consistent with the phase's precedents, but "declining the source should auto-decline its packages" is a defensible alternative nobody has ruled on.
4. **Whether a package whose repository is inert should keep being offered at all.** Follows from (3); the current behaviour — offer forever, fail forever — is the one option that is certainly wrong, but which of the alternatives applies is a user call.</result>

## What the model is now

An apt signing key is **not an item**. `ItemClass.APT_KEY` and `AptKeyItem` are deleted; there is no `apt:key:` identity anywhere in the codebase (verified by grep across `src/`, `docs/`, `tests/`). Keys are two file operations bracketing the repository group in `src/pcswitcher/jobs/apt_sync.py`:

- **`_provision_keyrings`** — before any source write. Copies every `/etc/apt/trusted.gpg.d` key the target lacks or differs on, plus every keyring referenced by a source that will exist on the target, matched on **content**, not presence. `/etc/apt/keyrings` is never mirrored wholesale.
- **`_remove_unused_keyrings`** — after every source write and deletion, gated on the run having removed a source. Counts references from a **fresh** `_scan_target_source_references` of the target's real post-write state.

## Answers to your questions

**Global-trust keys**: replicated (missing *and* differing — I refresh on content, my call), never collected. Justification: nothing references a `trusted.gpg.d` file by construction, so "unused" is not computable and content difference is the only signal that exists in either direction; deleting one would be a guess against ambient trust that apt uses for every repo without a `Signed-By:`.

**Existing recorded key decisions**: none possible, by construction — a key never reaches a `ReviewGroup`, so `_record_permanent_skips` has nothing to record. `blk:test_a_signing_key_is_never_offered_and_so_can_never_be_recorded` drives a full `SKIP_ALWAYS`-everything review over a target-only orphaned keyring and asserts neither machine's decision file is written. No migration branch exists.

**Strand-a-repo guard**: it is not a guard. It *is* how the removal set is derived — the reference count runs against the target's actual state after all repository operations, so a declined removal, a failed removal, a machine-specific repo and `/etc/apt/sources.list` all keep their key alive without any special case. I extended the scan to cover `/etc/apt/sources.list` (never synced, so always survives).

**Rotation**: fixed as instructed. `test_rotated_keyring_is_refreshed_although_its_source_file_is_identical` asserts the plan has **zero** diffs and the key is still promoted. The trigger is `_pending_keyring_work()` in `accept_review`, which inserts the metadata-refresh marker so the group runs at all; it is a decision-independent superset and the group recomputes the exact set and returns early if empty.

**Judgement calls to flag**
1. A `Signed-By:` pointing outside `/etc/apt/keyrings` and `/etc/apt/trusted.gpg.d` (e.g. `/usr/share/keyrings/ubuntu-archive-keyring.gpg`) is not provisioned — pre-existing `_dangling_keyring_ref` behaviour already downgrades such a repo to `REPORT_ONLY`, and I did not change it.
2. Key provisioning/collection only runs when the repository group runs. Global-trust key work is itself a trigger, so an ambient-trust-only difference still converges; a pins/config-only run also provisions.
3. Dry-run shows no key activity (the group never converges under `--dry-run`).

**Mutation-checked** (each reverted after): counting references against the plan-time scan instead of the post-write one (2 fail); deleting referenced keys (4); collecting with no source removed (1); collecting global-trust keys (1, after I strengthened that assertion — my first mutation was mis-targeted and survived); presence-based instead of content-based provisioning, i.e. no rotation (2); mirroring `/etc/apt/keyrings` wholesale (2); departing repo still counting as a reference (1); `_require_keyrings_ready` never refusing (2); dropping `/etc/apt/sources.list` from the scan (12); removing the rotation trigger from `accept_review` (3).
