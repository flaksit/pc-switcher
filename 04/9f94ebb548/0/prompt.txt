## The article text

`PKG-FR-BLOCKS-REPLICATE` now carries the general rule; the three per-manager articles carry their own halves.

&gt; **PKG-FR-BLOCKS-REPLICATE**: An apt hold, a snap refresh hold and a flatpak mask MUST each replicate as an item decided separately from the software it applies to — EXCEPT where that software is itself an item in the same run, in which case the two MUST be presented as one question that names both, and the decision given there MUST govern both. Which case a block is in is decided by whether its software carries a decision this run: software that is only reported is no item, and a block that names its software by pattern rather than by name rides a question only where the pattern covers exactly one of this run's items. The merged question MUST take the software's own direction and therefore its default (`PKG-FR-HARMLESS-DEFAULT`). Applying it MUST converge the software as its own article requires and the block to the source's state — except that a block which freezes an installed copy, an apt hold or a snap refresh hold, MUST NOT be registered for software the target does not end the run with, and MUST there be reported as not applied rather than as a failure. Declining for this run MUST leave both unchanged and record nothing. A machine-specific mark given on the merged question MUST be recorded for the software AND for the block, each on its own holding machine.

Four *Why* lines follow it: the contradiction the two questions hide; why the mark covers both (otherwise the block returns alone next run, about software the tool was just told to leave alone); why the software's default governs (a block is not software, so `PKG-FR-REMOVAL-DISTINCT` is not engaged, and the merge only ever makes the default safer in the other direction); and why the exception is narrow.

`PKG-FR-APT-HOLD-ITEM` and `PKG-FR-SNAP-HOLD` add the same exception plus "a hold MUST NOT be registered for a package the target does not end the run with". `PKG-FR-FLATPAK-MASK` adds the exactly-one-match boundary and states that a mask riding a removal still lands — a mask is a rule about what may be installed, not a freeze on an installed copy, which is the one place the three block kinds diverge.

**The four decisions, resolved:** apply → software converges, then the block, except a freeze block whose software is leaving (reported not-applied, never a failure); skip once → both unchanged, nothing recorded; machine-specific → two marks, each on its own holding machine (for B41 that is two *different* machines: `apt:package:pkg-a` on Nomad, `apt:hold:pkg-a` on Atlas); the block's own direction is what picks its file, so the write path was already correct once the decision propagates.

<result># Design: a second review round, built from the first round's answers

`PackageSyncJob.plan_second_round(plan, outcome)` — new hook on `sync_core.py`, no-op on the base. It returns the run's **final** item set as `diffs` and the **second round's** groups alone. `execute()` calls it between the two reviews, merges the answer sets (`_merge_rounds`), and raises `JobSkipped` when *either* round holds something a run with no terminal cannot answer. Reads only; both rounds precede every change.

**`PKG-FR-BATCHED` licenses it, not `PKG-FR-ASK-AGAIN`.** The rounds come one after another with no work between them and each recurring kind of decision is still settled in one pass, which is exactly what the article asks. `PKG-FR-ASK-AGAIN` is a different permission — asking *after the target has been changed* — and it is what licenses `LateCollateral`'s round, which is now the third. No conflict arose, so nothing was stopped.

`AptSyncJob.plan_second_round` is the only implementation. It resolves the first round's collateral answers first (one can withdraw a removal a repository is counted against), then builds the three questions.

## Per-item-kind analysis

I enumerated every `CHANGE` producer in the codebase. There are only two the user can ever mark, and both are the same shape — the item is on **both** machines:

| CHANGE item | Article | Whose state the mark describes |
| --- | --- | --- |
| `apt:config:&lt;file&gt;` (`/etc/apt/apt.conf.d`) | `PKG-FR-APTCONF` | **Target.** The answer refuses the overwrite of the target's copy. |
| `snap:&lt;name&gt;` (revision and/or channel) | `PKG-FR-SNAP-CASES`, `PKG-FR-SNAP-REVISION` | **Target.** Same: it keeps the target's revision/channel. |
| `apt:metadata-refresh` (synthetic) | — | Never reviewed; `accept_review` forces it to `APPLY`, so it can never be marked. Unreachable, left alone. |

Nothing else produces a `CHANGE`. ## 1. The near-miss check

`tests/unit/test_scenario_coverage_matrix.py::test_no_docstring_opens_with_a_tag_the_matcher_cannot_read`

Rule: a docstring whose **first position** holds a scenario id — bare, or wrapped in the punctuation a tag gets typed with (`` ` ``, `(`, `[`, quote, `*`) — but which `DOCSTRING_TAG` cannot parse, is an error naming `Class::test` and the id.

How I drew the boundary. I scanned all test-class methods with three candidate rules:

- **Mentions an id anywhere, no tag** — fires on **1** test, `test_apt_etc_apt:…::test_a_package_apt_reports_no_candidate_for_is_withheld_from_the_first_pass`, which opens *"The other half of what N5's ordering test cannot show: …"*. That is legitimate prose, so the broad rule is wrong.
- **Id anywhere in the opening clause** (before the first `—`/`:`/`.`) — same false positive: N5 sits before that docstring's first colon.
- **Id in first position** — fires on **0** existing tests, and position 0 is the only place a tag ever sits, so a lead id that fails to parse can only be a broken tag.

<result>## What the scan did

`_UNOWNED_SCAN_ROOTS = ("/usr/local", "/opt", "/usr/local/bin", "/usr/local/lib")` — one shell loop runs `find &lt;root&gt; -mindepth 1 -maxdepth 1` over all four. Two of the four roots (`/usr/local/bin`, `/usr/local/lib`) are also **entries of** a third (`/usr/local`), so `find` emitted them as ordinary candidates; they then went into the batched `dpkg --search` like any other path, and anything dpkg didn't claim became an `UnreproducibleItem` demanding an install snippet. That is exactly the both-a-root-and-an-entry duplication G28's register history describes. Nothing anywhere filtered them.

Confirmed on this machine (read-only `dpkg --search`): `/usr/local/lib`, `/usr/local/etc`, `/usr/local/games`, `/usr/local/include`, `/usr/local/man`, `/usr/local/sbin`, `/usr/local/src` — *no path found*; `/usr/local/bin` claimed only incidentally by `cnpg`. ## Verdict: it is a product defect

I agree with your reading. `PKG-FR-MANUAL-SCOPE` covers *software under* `/usr/local` and `/opt`; a directory the scan itself descends into is not software under itself, and the user requirements' own wording ("dropped there by an install script or a tarball") excludes a directory the distribution ships. Ownership can't rescue it either — dpkg owns no `/usr/local` directory on stock Ubuntu, so the finding is not machine-specific noise but universal noise. The integration test is right and is untouched.
