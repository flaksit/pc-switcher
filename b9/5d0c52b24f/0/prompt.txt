## Task 2 — probe failure vs. wrong request

### How I tell "apt answered nothing" from "the probe failed"

`_require_apt_answer` (`apt_sync.py:1316-1346`), two conditions and no others:

1. **Non-zero exit.** Measured in a stock `ubuntu:24.04` container: `apt-cache policy &lt;unknown-name&gt;` exits **0** and prints nothing; a broken sources config exits **100** with `E:` on stderr and empty stdout. Corrupt lists, unreadable cache, unprivileged user, bad apt.conf all still exit 0 and answer. So a non-zero exit is never a statement about a package. Unambiguous.
2. **Zero blocks parsed where the caller knows at least one was owed.** Measured on this machine: `apt-cache policy $(apt-mark showmanual)` → 152 names, 152 blocks, exit 0. This one is **a judgement, not a discrimination**, and the code says so: a probe that answered "I know none of these" and a probe that died both print nothing, and the output cannot separate them. I resolved it toward fail-fast, and stated the cost in the docstring — a single-name set whose one name apt legitimately never heard of now fails the run instead of refusing one item.

Per-name absence *inside* an answered probe is untouched: it stays a per-item `ConvergeItemFailed` ("offers it from no repository at all"). That is the asymmetry you asked me not to break, and the plan-time rule (`_OriginPlan.target_candidate_known`, `df48cd07`) is untouched.

`AptProbeFailed` subclasses `RuntimeError`, **not** `ConvergeItemFailed`, so it escapes `_converge_one`'s `except` (`sync_core.py:456`) and fails once. Note the downstream consequence I did not change: the orchestrator's default `except Exception` arm (`orchestrator.py:1315-1330`) records the job FAILED **and re-raises**, aborting the run. That is the existing "every other exception keeps today's abort-the-run behavior" policy, not a new decision — flagging it because an apt probe failure now aborts `folder_sync` too.
