## How "machine-specific" is determined, and that it matches apt

apt: `apt_sync.py:2128` — `_source_decisions, target_decisions = self._plan_decisions`, then every item id in the TARGET's decision file with the `apt:package:` prefix. `DecisionFile.load()` (`state.py:189`) returns exactly the skip-always entries (`state.py:96-99`: "Every entry below came from an explicit skip always choice").

flatpak (`flatpak_sync.py:1276`): `[ref for ref in installed_target_refs if ref.item_id in target_decisions]`, where `installed_target_refs` is the UNFILTERED target listing (`flatpak_sync.py:1219`) — i.e. exactly the set `filter_inert` removed. Same file, same meaning. **Not** target-only. Mutation M1 pins it.

Two further narrowings, both documented at `flatpak_sync.py:1247-1274`:
- the remote must be in `_derive_remotes`' output over the *proposed* installs (a superset of what `accept_review` derives). This is a deliberate divergence from apt, whose screen covers every changed file and whose approval force-writes it (`apt_sync.py:2492-2496`). Flatpak's doctrine is "a remote travels because a ref needs it", so asking about a remote nothing will touch would describe a change that was never going to happen, and answering "overwrite" must not itself make one travel.
- `target_item is not None` — a remote the target lacks is an ADD, replacing nothing.

`key_digest` is excluded from the trigger (`_PROVENANCE_FACETS`, `flatpak_sync.py:213-217`): `--gpg-import` merges into the ostree keyring rather than replacing it — the same measured fact `_origin_refusal` already cites for not comparing digests — so it can neither move an origin nor withdraw trust. A key-only difference stays silent.

## What the screen shows, and why

`versions=(target_text, source_text)`, one **differing facet per line**, target's panel first (`_remote_conflict_versions`, `flatpak_sync.py:822`). e.g. target `url: https://old.mirror…/repo/` / source `url: https://dl.flathub.org/repo/`; a trust divergence adds `gpg verification: disabled` / `enabled`.

Never `_remote_change_detail`'s `A vs B` form — that is a computed difference, and the user's verdict on apt's version ("diff is not very readable") rules it out. apt shows two whole file bodies because a repository file *is* a body; a remote is a handful of named values, so the readable answer is the fields that disagree, printed twice. `_remote_facets` is now the single definition of "differs" behind both renderings, so the log line and the screen cannot drift. Costs **no command** — the record is already on `FlatpakRemoteItem` (apt pays two `cat`s per entry).

## What a skipped conflict does — and yes, `_origin_refusal` already covered it

Skipped/undecided → the remote leaves `self._derived_remotes` but stays in `_ref_derived_remote_ids`, and `_failed_derived_remotes` is seeded (`accept_review`, `flatpak_sync.py:1421-1428`). Every approved ref that named it fails as its own item (D-27/D-39).

**`_origin_refusal` already covers the wrong-vendor outcome on its own — verified, not assumed.** With the seeding mutated away (M7), the ref is still not installed; the message merely becomes the generic one:

&gt; `install of org.example.App/x86_64/stable refused: the target's user-scope remote 'flathub' points at https://old.mirror.example.org/repo/, but the source takes this ref from https://dl.flathub.org/repo/ — same name, different repository…`

So the seeding is **not** a second safety mechanism and I added none: it reuses the existing `_failed_derived_remotes` dict, and its only effect is that the failure names the user's own decision (checked first in `_converge_ref:1372`) instead of the symptom.
